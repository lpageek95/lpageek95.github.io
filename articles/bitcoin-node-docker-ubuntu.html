Running a Bitcoin Full Node on Ubuntu with Bitcoin Core in Docker

Crypto · ■■□ Intermediate · 18 min read · Published Oct 19, 2026

  • bitcoin
  • docker
  • linux
  • ubuntu

How to run your own Bitcoin full node on an Ubuntu server: download and cryptographically verify Bitcoin Core, package it in a small Docker image, keep the blockchain on persistent storage, accept inbound peers on port 8333, and follow the sync with bitcoin-cli.

Credit

Inspired by Red Fox Crypto's video How to Run Your Own Bitcoin Node (Step-by-Step), which installs Bitcoin Core by hand inside an Ubuntu container on a NAS. This guide follows the same path (verify, install, persist, open 8333, auto-start) on a plain Ubuntu host, and bakes the install into a Dockerfile so the container can be rebuilt or upgraded with one command.

Introduction

A Bitcoin full node downloads every block since 2009 and checks every rule itself: signatures, the 21 million coin limit, block sizes, double-spends. It doesn't trust miners, exchanges or block explorers to tell it what's valid. If you hold bitcoin, your own node is the way to verify your balance and transactions without asking someone else.

Running the node in Docker keeps the host clean: the Bitcoin Core binaries live in an image, the blockchain lives in a directory on the host, and upgrading means rebuilding the image and recreating the container. The blockchain data survives every rebuild.

When this is useful

  • You want to verify Bitcoin yourself instead of trusting a third-party server.
  • You want a backend for your own wallet (Sparrow, Electrum via an Electrum server, a Lightning node) later on.
  • You want to help the network by serving blocks to other nodes.
  • You already run a home server or lab box with Docker and want to add a node to it.
  • You want a hands-on way to learn how Bitcoin works under the hood.

Prerequisites

ResourceMinimumRecommended
OSUbuntu 22.04 LTSUbuntu 24.04 LTS, x86_64
Storage~10 GB with pruning2 TB SSD for a full (unpruned) node. The chain is well over 700 GB in 2026 and keeps growing.
RAM2 GB8 GB or more (a bigger dbcache makes the first sync much faster)
CPU2 cores4+ cores
NetworkStable broadbandNo tight data cap. The first sync downloads the whole chain, and a listening node can upload hundreds of GB per month.
  • Shell access with sudo.
  • Access to your router if you want inbound connections (port forwarding for TCP 8333).
  • Examples use Bitcoin Core 31.1, the newest release at the time of writing. Check bitcoincore.org/en/download and use the current version everywhere you see 31.1.
Use an SSD

A node on a spinning disk works, but the initial sync can take weeks instead of a day or two because validating blocks does a huge amount of random I/O. If the SSD is a second drive, mount it (for example at /srv) before you start.

How a Bitcoin node works

A node does three jobs:

  • Historian. It stores the blockchain and serves old blocks to other nodes that are syncing.
  • Enforcer. It validates every block and transaction against the consensus rules and rejects anything invalid, no matter who mined it.
  • Mempool host. It keeps a pool of valid unconfirmed transactions and relays them to its peers.

The pieces in this setup:

PieceWhat it is
bitcoindThe Bitcoin Core daemon. It talks to peers, validates and stores the chain.
bitcoin-cliCommand-line client that sends RPC calls to bitcoind on port 8332.
Port 8333Peer-to-peer port. Published to the internet so other nodes can connect to you.
Port 8332RPC port. Never exposed. In this setup it stays inside the container.
/srv/bitcoinData directory on the host, mounted into the container. Holds blocks, the chainstate (UTXO set), bitcoin.conf and debug.log.
Docker imageUbuntu 24.04 plus the verified Bitcoin Core binaries, running as an unprivileged bitcoin user.

The first start triggers the initial block download (IBD). The node fetches headers, then every block, and validates them in order. Progress is reported as verificationprogress, a number from 0 to 1. Until it gets close to 1 the node isn't fully in sync and shouldn't be relied on.

Setup workflow

1. Install Docker Engine

Use Docker's own apt repository (the docker.io package in Ubuntu works too, but lags behind):

sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg jq xxd
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker

# Optional: run docker without sudo (log out and back in afterwards)
sudo usermod -aG docker "$USER"

jq and xxd are used later to read bitcoin-cli output.

Warning

Members of the docker group are effectively root on the host. Only add users you'd also give sudo.

docker --version
docker compose version
docker run --rm hello-world

2. Download Bitcoin Core

Work in a project directory. It becomes the Docker build context:

mkdir -p ~/bitcoin-node && cd ~/bitcoin-node

VERSION=31.1
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/bitcoin-${VERSION}-x86_64-linux-gnu.tar.gz
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/SHA256SUMS
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/SHA256SUMS.asc

The tarball is the program. SHA256SUMS lists the hash of every release file, and SHA256SUMS.asc holds signatures over that list from Bitcoin Core's builders. On an ARM board (Raspberry Pi 5 with a 64-bit OS) download aarch64-linux-gnu instead.

3. Verify the download: checksum and signatures

Don't skip this. You're about to run software that will guard money, and verification proves the file is exactly what the Bitcoin Core developers built and signed, not something swapped on a mirror or in transit.

Checksum: is the file intact and listed in SHA256SUMS?

sha256sum --ignore-missing --check SHA256SUMS
bitcoin-31.1-x86_64-linux-gnu.tar.gz: OK

Signatures: was SHA256SUMS signed by the people who build Bitcoin Core? Import their public keys from the guix.sigs repository, then verify:

git clone --depth 1 https://github.com/bitcoin-core/guix.sigs
gpg --import guix.sigs/builder-keys/*
gpg --verify SHA256SUMS.asc SHA256SUMS

You want several lines of Good signature from "...". See Reading the output for what the warnings mean. A single BAD signature means stop: delete the files and download again.

4. Prepare the data directory and bitcoin.conf

The blockchain must live outside the container so it survives rebuilds. The container runs as UID 1001 (UID 1000 is already taken by the ubuntu user in the base image), so that UID must own the directory: 

sudo mkdir -p /srv/bitcoin
sudo chown 1001:1001 /srv/bitcoin

Create /srv/bitcoin/bitcoin.conf (for example with sudo nano):

# Enable the RPC server so bitcoin-cli works (it stays inside the container)
server=1
rpcbind=127.0.0.1
rpcallowip=127.0.0.1

# Accept inbound peer connections on 8333
listen=1

# UTXO cache in MiB. A bigger value makes the first sync much faster.
# About half your RAM during the sync; drop it to 450-1000 afterwards.
dbcache=4096

# Optional: limit upload to N MiB per 24h if your plan has a data cap
#maxuploadtarget=5000

# Optional: pruned node. Keeps only the last N MiB of blocks (minimum 550).
# Still validates everything, but can't serve old blocks to peers.
#prune=50000
sudo chown 1001:1001 /srv/bitcoin/bitcoin.conf
sudo chmod 600 /srv/bitcoin/bitcoin.conf

No RPC username or password is needed: bitcoind writes a random cookie to /srv/bitcoin/.cookie at startup, and bitcoin-cli inside the container reads it automatically.

5. Write the Dockerfile

In ~/bitcoin-node, next to the verified tarball:

FROM ubuntu:24.04

ARG BITCOIN_VERSION=31.1
ARG BITCOIN_UID=1001

# The tarball was downloaded and verified on the host (steps 2-3)
COPY bitcoin-${BITCOIN_VERSION}-x86_64-linux-gnu.tar.gz /tmp/bitcoin.tar.gz

RUN tar -xzf /tmp/bitcoin.tar.gz -C /tmp \
 && install -m 0755 /tmp/bitcoin-${BITCOIN_VERSION}/bin/bitcoind \
                    /tmp/bitcoin-${BITCOIN_VERSION}/bin/bitcoin-cli /usr/local/bin/ \
 && rm -rf /tmp/bitcoin.tar.gz /tmp/bitcoin-${BITCOIN_VERSION} \
 && useradd --create-home --uid ${BITCOIN_UID} bitcoin

USER bitcoin
VOLUME ["/home/bitcoin/.bitcoin"]
EXPOSE 8333

CMD ["bitcoind", "-printtoconsole"]

Copying the tarball you verified (instead of downloading inside the build) means the image contains exactly the bytes you checked. The release binaries are self-contained, so the base image needs no extra packages. -printtoconsole sends the log to docker logs as well as debug.log.

6. Write the Compose file

services:
  bitcoind:
    build:
      context: .
      args:
        BITCOIN_VERSION: "31.1"
    image: local/bitcoind:31.1
    container_name: bitcoind
    restart: unless-stopped      # start on boot, restart after crashes
    init: true                   # proper signal handling and zombie reaping
    stop_grace_period: 10m       # give bitcoind time to flush its database
    ports:
      - "8333:8333"              # P2P only. Never publish 8332 (RPC).
    volumes:
      - /srv/bitcoin:/home/bitcoin/.bitcoin
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "3"

stop_grace_period matters: Docker's default is 10 seconds, after which it kills the process. bitcoind often needs longer than that to write its cache to disk, and a hard kill during the sync can force a long replay or even a reindex. restart: unless-stopped together with systemctl enable docker is what brings the node back after a reboot.

7. Build and start the node

cd ~/bitcoin-node
docker compose up -d --build
docker compose logs -f bitcoind      # Ctrl+C stops following, not the node

Make bitcoin-cli convenient with an alias in ~/.bashrc:

echo "alias btc='docker exec bitcoind bitcoin-cli'" >> ~/.bashrc
source ~/.bashrc

8. Follow the sync

btc -getinfo                              # quick dashboard with a progress bar
btc getblockchaininfo | jq '{blocks, headers, progress: (.verificationprogress * 100),
                             ibd: .initialblockdownload, size_gb: (.size_on_disk / 1e9)}'
du -sh /srv/bitcoin                       # disk used so far

The first few years of blocks fly by because they're small. Progress slows down a lot from around 2016 on, when blocks got full. With an SSD, 8 GB of RAM and decent bandwidth, expect roughly one to two days; on a Raspberry Pi or a hard disk, much longer.

9. Make the node reachable from the internet

Your node already works with outbound connections only: it validates everything and is fully useful to you. Opening port 8333 lets other nodes connect to you too, which is how you help the network.

  1. Give the server a fixed LAN IP (a DHCP reservation on the router is easiest).
  2. On the router, forward TCP 8333 to that IP.
  3. Wait a while (new nodes get discovered gradually), then check:
btc getnetworkinfo | jq '{connections, connections_in, connections_out, localaddresses}'

connections_in above 0 means someone reached you. You can also enter your public IP and port 8333 in the "check node" tool on bitnodes.io.

Docker and ufw

Ports published by Docker bypass ufw: Docker writes its own iptables rules, so 8333:8333 is open on every interface even if ufw says otherwise. That's fine for 8333, which is meant to be public. It's also why you must never add 8332:8332 to the Compose file. Anyone who reaches the RPC port can control the node.

10. Bonus: read Satoshi's message in the genesis block

Block 0 contains a newspaper headline that Satoshi Nakamoto embedded in its coinbase transaction. Your own node can show it to you:

btc getblockhash 0
btc getblock "$(btc getblockhash 0)" 0 | xxd -r -p | strings

getblock <hash> 0 returns the raw block as hex, xxd -r -p turns the hex back into bytes, and strings prints the readable text. 

000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f
EThe Times 03/Jan/2009 Chancellor on brink of second bailout for banks

The headline timestamps the block (it can't have been mined before that newspaper was printed) and hints at why Bitcoin was created. The stray E is the length byte of the text in the script.

Upgrading to a new Bitcoin Core release

cd ~/bitcoin-node
VERSION=31.2      # the new release
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/bitcoin-${VERSION}-x86_64-linux-gnu.tar.gz
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/SHA256SUMS
curl -fLO https://bitcoincore.org/bin/bitcoin-core-${VERSION}/SHA256SUMS.asc
git -C guix.sigs pull && gpg --import guix.sigs/builder-keys/*
sha256sum --ignore-missing --check SHA256SUMS && gpg --verify SHA256SUMS.asc SHA256SUMS

# Update BITCOIN_VERSION and the image tag in docker-compose.yml, then:
docker compose up -d --build

Compose stops the old container gracefully, starts the new one, and the node continues from the same data in /srv/bitcoin. Read the release notes first: major versions occasionally change defaults or config options.

Reading the output

gpg --verify

gpg: Signature made Wed 08 Jul 2026 ...
gpg:                using RSA key 101598DC823C1B5F9A6624ABA5E0907A0380E6C3
gpg: Good signature from "CoinForensics (SigningKey) <...>" [unknown]
gpg: WARNING: This key is not certified with a trusted signature!
gpg:          There is no indication that the signature belongs to the owner.
gpg: Signature made Wed 08 Jul 2026 ...
gpg: Good signature from "fanquake <...>" [unknown]
...

Good signature is what matters: the file matches the key. The WARNING only says you haven't personally certified those keys in your web of trust, which is normal. The more independent builders that sign, the stronger the evidence. One or two Can't check signature: No public key lines are fine (keys you didn't import); BAD signature is not.

docker compose logs during the sync

bitcoind  | UpdateTip: new best=00000000000000000002a7c4... height=612403 version=0x20000000
            log2_work=91.95 tx=488012350 date='2019-12-30T14:21:07Z' progress=0.392118 cache=3012.4MiB(21934117txo)
bitcoind  | Synchronizing blockheaders, height: 920114 (~100.00%)

height is the block being validated, date is when that block was mined, and progress is the same 0–1 value as verificationprogress (here 39%). cache growing toward your dbcache is normal; when it fills, the node flushes it to disk and briefly slows down.

btc -getinfo

Chain: main
Blocks: 612403
Headers: 920114
Verification progress: ▒▒▒▒▒▒▒░░░░░░░░░░░░░ 39.2118%
Difficulty: 15546745765549.48

Network: in 0, out 10, total 10
Version: 310100
Time offset (s): 0
Proxies: n/a
Min tx relay fee rate (BTC/kvB): 0.00001000

Warnings: (none)
  • Blocks vs Headers: headers arrive first and are cheap; Blocks catches up as each one is validated. When they are equal and progress is ~100%, you're in sync.
  • Network: in 0, out 10: 10 outbound peers is the default. in 0 is expected until port 8333 is forwarded and other nodes find you.
  • Version 310100 = 31.1.0.

getblockchaininfo when fully synced

{
  "blocks": 920114,
  "headers": 920114,
  "progress": 99.99991,
  "ibd": false,
  "size_gb": 762.4
}

ibd: false means the initial block download is finished. Progress rarely shows exactly 100 because it's an estimate based on time since the last block.

Common problems

The container keeps restarting: permission errors on the data directory

Symptoms
docker compose ps shows Restarting, and the log complains it can't create or write files under /home/bitcoin/.bitcoin.
Possible causes
/srv/bitcoin or bitcoin.conf is owned by root (or UID 1000) instead of the container's UID 1001.
Investigation
docker compose logs --tail 30 bitcoind
ls -lan /srv/bitcoin | head
docker run --rm local/bitcoind:31.1 id      # shows the UID the image runs as
Resolution
sudo chown -R 1001:1001 /srv/bitcoin
docker compose up -d
Verification
The status changes to Up and the log shows UpdateTip lines.

bitcoin-cli returns an error

Symptoms
error code: -28
error message:
Loading block index…

or error: Could not connect to the server 127.0.0.1:8332.

Possible causes
Code -28 means bitcoind is still starting (loading the block index, verifying recent blocks) and is not an error: wait and retry. "Could not connect" means bitcoind isn't running, or server=1 / the rpcbind lines are wrong in bitcoin.conf.
Investigation
docker compose ps
docker compose logs --tail 50 bitcoind
docker exec bitcoind cat /home/bitcoin/.bitcoin/bitcoin.conf
Resolution
Fix the config, then docker compose restart bitcoind. Run bitcoin-cli through docker exec as shown; running it on the host won't find the cookie or the RPC port.

The initial sync is very slow

Symptoms
Progress moves a fraction of a percent per hour, especially past 2016-era blocks.
Possible causes
A hard disk or USB-attached disk, a small dbcache, too little RAM (the host is swapping), or slow bandwidth.
Investigation
free -h                               # swapping?
iostat -x 5 3                         # %util near 100 on the data disk = I/O bound (package: sysstat)
docker stats --no-stream bitcoind
btc getblockchaininfo | jq '.verificationprogress'
Resolution
Raise dbcache as far as your free RAM allows during the sync, then lower it afterwards. Move /srv/bitcoin to an SSD if it's on a hard disk. Don't stop and start the node repeatedly: each clean stop flushes the cache, and the speed-up from a big cache is lost.

No inbound connections

Symptoms
connections_in stays at 0 after a day, and bitnodes.io reports the node as unreachable.
Possible causes
No port forward or a wrong target IP, the server's LAN IP changed, or your ISP uses carrier-grade NAT (your router's WAN IP is not your public IP), which blocks inbound connections entirely.
Investigation
docker compose port bitcoind 8333     # should print 0.0.0.0:8333
sudo ss -tlnp | grep 8333             # is the host listening?
ip -4 addr show                       # server's LAN IP: does the router forward to it?
curl -4 https://ifconfig.me           # public IP: compare with the router's WAN IP
Resolution
Fix the forward or the DHCP reservation. If you're behind CGNAT, ask your ISP for a public IP, or accept an outbound-only node, which still fully validates and is completely fine for your own use.

"Corrupted block database detected" after a crash or power loss

Symptoms
The node won't start and the log says Error: Corrupted block database detected and suggests -reindex or -reindex-chainstate.
Possible causes
A power cut, an out-of-memory kill, or a container killed before bitcoind finished flushing (for example, the default 10-second stop timeout).
Resolution

Try the cheaper option first. Temporarily override the command, let it finish, then go back to the normal command:

docker compose run --rm --service-ports bitcoind bitcoind -printtoconsole -reindex-chainstate
# If that fails, the full reindex (re-reads every block file from disk):
docker compose run --rm --service-ports bitcoind bitcoind -printtoconsole -reindex
Warning

Stop the normal container first (docker compose stop): two bitcoind processes can't use the same data directory. A reindex can take as long as the original sync. Prevent a repeat with stop_grace_period, enough RAM, and ideally a UPS.

The disk fills up

Symptoms
bitcoind shuts down with Error: Disk space is too low!, and the container restart-loops.
Investigation
df -h /srv
sudo du -sh /srv/bitcoin/blocks /srv/bitcoin/chainstate /srv/bitcoin/indexes 2>/dev/null
docker system df
Resolution
Move /srv/bitcoin to a larger disk (stop the node, copy, update the volume path), or switch to a pruned node by adding prune= to bitcoin.conf. Pruning can't be combined with txindex=1, and turning pruning off again later means downloading the whole chain again. See the Linux disk space guide for finding other space consumers on the host.

Troubleshooting tips

  • debug.log in /srv/bitcoin has more detail than docker logs, and survives container recreation: sudo tail -f /srv/bitcoin/debug.log.
  • btc help lists every RPC, and btc help getblockchaininfo documents each field.
  • docker compose ps shows a restart counter in the status column: a node that restarts every few minutes is failing at startup, so read the log from the top of the last start.
  • Clock matters. If Time offset in -getinfo is large, fix NTP on the host (timedatectl status).
  • To test the whole setup in minutes instead of days, run a throwaway copy on signet (add -signet and use a separate data directory).

Best practices

  • Verify every release with both the checksum and the signatures before building the image.
  • Never publish the RPC port 8332. If another container needs RPC (a wallet server, a Lightning node), put both on a private Docker network and set rpcallowip to that network.
  • Run the node as an unprivileged user (UID 1001 here), never as root inside the container.
  • Keep the stop timeout long and the host on a UPS if you can. Unclean shutdowns are the main cause of reindexes.
  • Pin the version in the image tag (local/bitcoind:31.1) so you always know which release is running, and read the release notes before upgrading.
  • The blockchain doesn't need backups (it can always be downloaded again). Back up bitcoin.conf, and any wallet if you create one.
  • Keep the Ubuntu host patched (unattended-upgrades) and limit who can SSH in. The node is a long-running internet-facing service.

Summary

  1. Install Docker Engine and Compose on Ubuntu from Docker's repository.
  2. Download Bitcoin Core, then verify it with sha256sum --check and gpg --verify against the builders' keys.
  3. Create /srv/bitcoin (owned by UID 1001) with a bitcoin.conf.
  4. Build an image from the verified tarball and run it with Compose: persistent volume, port 8333 published, RPC kept private, long stop timeout, restart: unless-stopped.
  5. Follow the sync with bitcoin-cli -getinfo and getblockchaininfo, forward TCP 8333 on the router, and confirm inbound peers.
