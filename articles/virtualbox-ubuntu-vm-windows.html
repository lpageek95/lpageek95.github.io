Running an Ubuntu Server VM on Windows with VirtualBox

Introduction

A VirtualBox VM is the cheapest way to get a real Linux server on a Windows desktop. The defaults suit a desktop VM you use from its own window, not a headless server you SSH into and run Kubernetes on. Four things in particular trip people up: a wizard that won't continue, an installer that uses only half the disk, a NAT network you can't reach, and a Windows hypervisor that hides CPU instructions from the guest.

I hit all four while building the node for my self-hosted LLM on k3s project.

When this is useful

  • You want a Linux lab server (Kubernetes, Docker, databases) on a Windows PC.
  • You can't SSH into your VM from Windows or from other devices.
  • df -h / inside the VM shows about half the disk you gave it.
  • Workloads in the VM are much slower than expected, or /proc/cpuinfo is missing avx2.
  • VirtualBox shows a green turtle icon in the VM's status bar.

Prerequisites

  • Windows 10 or 11 with administrator rights.
  • VirtualBox 7.x and the Ubuntu Server 24.04 LTS ISO (ubuntu-24.04.x-live-server-amd64.iso).
  • Hardware virtualization enabled in the BIOS/UEFI (Intel VT-x or AMD-V/SVM). Check in Task Manager → Performance → CPU → "Virtualization: Enabled".
  • Enough RAM to split between Windows and the VM. On a 16 GB PC, give the VM 8 GB.

Create the VM

Name, ISO and unattended install

  • The Next button stays grey until the VM has a name. Selecting the ISO isn't enough.
  • Tick "Skip Unattended Installation". Unattended mode installs Ubuntu with defaults. You'd miss the installer screens where you enable OpenSSH, choose your user and check the disk layout.

Install Ubuntu Server

  • Tick "Install OpenSSH server". You'll manage the VM over SSH, not from the VirtualBox console.
  • Skip the "Featured server snaps". In particular, don't install microk8s if you plan to run k3s or another Kubernetes distribution. Two distributions compete for the same ports and networking.

The installer only uses about half the disk

With the default "use an entire disk" + LVM layout, the installer creates the volume group on the whole disk but sizes the root logical volume at only part of it. On a 60 GB disk that gave a 28 GB root filesystem, and the rest sat unallocated. You can enlarge ubuntu-lv on the installer's storage screen, or fix it afterwards, live: 

sudo vgs        # VFree = unallocated space in the volume group
df -h /
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv   # -r resizes the filesystem as well
df -h /
Why it matters

Kubernetes evicts pods once free disk falls below its threshold (around 5% on the root filesystem). With container images and model files on a half-size volume, that happens sooner than you'd expect. My chat UI pod was evicted for exactly this reason.

Put the VM on your LAN

The default adapter mode is NAT. The VM gets a private 10.0.2.x address behind VirtualBox, can reach the internet, but can't be reached from Windows or the rest of the network. For a server, use Bridged Adapter. The VM then gets an address from your router, on the same subnet as your PC.

  1. Find which physical adapter Windows uses for the LAN. VirtualBox lists adapters by hardware name, not by the "Ethernet 2" connection name: 
    Get-NetAdapter | Select Name, InterfaceDescription, Status
  2. Power off the VM, then go to Settings → Network → Adapter 1 → Attached to: Bridged Adapter, and set Name to that InterfaceDescription.
  3. Don't pick the VirtualBox Host-Only adapter (a separate 192.168.56.x network) or any Hyper-V / vEthernet adapter.
  4. Boot the VM and check the address: 
    ip -4 addr show enp0s3     # should be on your LAN subnet, e.g. 192.168.1.x

The address comes from DHCP and can change. Create a DHCP reservation on your router for the VM's MAC address (VirtualBox MACs start with 08:00:27). Ingress hostnames and bookmarks then keep working.

Hyper-V and missing CPU features

When any part of the Windows hypervisor is active (Hyper-V, the Virtual Machine Platform used by WSL2, Windows Hypervisor Platform, or Memory Integrity), VirtualBox can't use VT-x/AMD-V directly. It runs the VM through the Windows hypervisor API instead. VirtualBox shows this as a green turtle in the VM's status bar. In this mode the guest can lose CPU features. On a Ryzen 7 5700X, which supports AVX2, the guest saw no avx, avx2, fma or f16c at all.

That matters for anything vectorized. CPU inference with llama.cpp/Ollama, compression and crypto libraries all fall back to much slower code paths.

Diagnose

grep -o -w 'avx\|avx2\|fma' /proc/cpuinfo | sort -u   # empty = features hidden
lscpu | grep -i 'model name\|hypervisor'

Hypervisor vendor: KVM in lscpu is normal. It's the paravirtualization interface VirtualBox presents to Linux guests, not a problem. 

Get-WindowsOptionalFeature -Online |
  Where-Object { $_.FeatureName -match 'Hyper-V|VirtualMachinePlatform|HypervisorPlatform' -and $_.State -eq 'Enabled' } |
  Select FeatureName
bcdedit /enum | findstr -i hypervisorlaunchtype

Fix

Trade-off

Turning the Windows hypervisor off disables WSL2, Docker Desktop, Windows Sandbox and Hyper-V VMs until you turn it back on. If you depend on those daily, accept the slower VM instead, or run the lab on a different machine.

Disable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All -NoRestart
Disable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -NoRestart
Disable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -NoRestart
bcdedit /set hypervisorlaunchtype off
  1. Also check Windows Security → Device security → Core isolation → Memory integrity. If it's on, it keeps the hypervisor loaded. Turn it off.
  2. Do a full Restart (not Shut down, which Fast Startup turns into hibernation).
  3. Start the VM. The turtle should be gone, and /proc/cpuinfo should list avx, avx2 and fma.

To undo it later:

Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All,VirtualMachinePlatform -NoRestart
bcdedit /set hypervisorlaunchtype auto
# then restart

Verification checklist

ip -4 addr show enp0s3                                # LAN address, not 10.0.2.x
df -h /                                               # root ≈ full disk size
free -h                                               # RAM as configured
nproc                                                 # vCPUs as configured
grep -o -w 'avx\|avx2\|fma' /proc/cpuinfo | sort -u   # avx, avx2, fma
systemctl is-active ssh                               # active

Then from Windows: ssh <user>@<vm-ip>.

Summary

  1. Name the VM, skip unattended install, give it 8 GB, 4–6 vCPU and a 60 GB dynamic disk.
  2. Install OpenSSH and skip the featured snaps.
  3. Grow the root LV to the full disk with lvextend -r.
  4. Use a Bridged Adapter on the physical NIC and reserve the IP on your router.
  5. If avx2 is missing, turn off the Windows hypervisor and restart.
