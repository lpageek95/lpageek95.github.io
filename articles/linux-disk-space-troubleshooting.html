Convention used in this article

Blue code blocks labelled read-only only inspect the system and are safe to run. Amber blocks labelled changes the system delete, truncate or modify something. Read the explanation before running them.

Introduction

A full filesystem rarely stays a small problem. When /var hits 100%, databases stop accepting writes, journald and application logs drop messages, package updates fail halfway through, and SSH logins can fail. The goal is to find the actual consumer quickly, free space safely, and then stop it happening again.

When this is useful

  • Monitoring alerts on filesystem usage (for example, over 85%).
  • Applications log No space left on device (ENOSPC).
  • df shows free space but writes still fail (inodes).
  • df shows the disk full, but du can't find the files (deleted-but-open files).
  • dnf update fails because /boot or /var is full.

Prerequisites

  • Shell access. Root or sudo is needed to see every directory and every process's open files.
  • lsof installed (dnf install lsof on RHEL if it's missing).
  • Examples assume RHEL 8/9 (XFS on LVM, dnf, systemd). The commands also work on other distributions, with different paths.

How disk usage is counted

Two different views of the same filesystem:

  • df asks the filesystem how many blocks are allocated. This is the truth about free space.
  • du walks the directory tree and adds up the files it can see.

They disagree when space is used by something that has no visible path:

  • Deleted files still held open by a process. rm removes the directory entry, but blocks are only freed when the last file descriptor is closed.
  • Files hidden under a mount point. Data written to /data before a filesystem was mounted there still uses space on the parent filesystem.
  • Reserved blocks (ext4 reserves 5% for root by default). XFS has no equivalent root-reserved percentage.

Separately, every file needs an inode. A filesystem can run out of inodes while plenty of blocks are still free, usually because of millions of tiny files.

Troubleshooting workflow

1. Which filesystem is full: blocks or inodes?

df -hT        # human-readable sizes plus filesystem type
df -i         # inode usage
df -h /var    # just the filesystem that contains /var

Always identify the filesystem first. /var/log being large doesn't matter if /var is its own logical volume with plenty of room.

2. Find the largest directories on that filesystem

# -x: stay on one filesystem (don't descend into /proc, NFS, other LVs)
sudo du -xh --max-depth=1 / 2>/dev/null | sort -h | tail -15

# Drill down into the biggest one and repeat
sudo du -xh --max-depth=1 /var 2>/dev/null | sort -h | tail -15

-x matters: without it, du / also counts every other mounted filesystem and sends you looking in the wrong place.

3. Find large and recently grown files

# Files over 500 MB on the /var filesystem
sudo find /var -xdev -type f -size +500M -exec ls -lh {} + 2>/dev/null

# Files over 50 MB modified in the last 60 minutes (what is growing right now?)
sudo find / -xdev -type f -size +50M -mmin -60 -exec ls -lh {} + 2>/dev/null

# Largest files in a directory
ls -lhS /var/log | head -15

4. If df and du disagree: deleted but open files

# Open files whose link count is 0 (deleted but still held open)
sudo lsof -nP +L1

# Alternative if lsof is unavailable
sudo find /proc/[0-9]*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null

The fix is to make the process close the file. See Deleted files still using space.

5. Check the usual suspects

sudo du -sh /var/log /var/log/journal /var/cache/dnf /var/lib/containers /var/lib/docker \
  /var/crash /var/lib/systemd/coredump /tmp /var/tmp 2>/dev/null
journalctl --disk-usage
rpm -q kernel                  # installed kernels (each one uses space in /boot)

6. Free space safely, then fix the cause

Prefer, in this order: rotate or compress → vacuum/clean with the owning tool → truncate → delete. Always use the tool that owns the data (journalctl, dnf, podman, logrotate) rather than rm on its files. Once the immediate pressure is gone, fix whatever caused the growth (log level, retention, a runaway job) or extend the filesystem.

Reading the output

df -hT

Filesystem            Type   Size  Used Avail Use% Mounted on
/dev/mapper/rhel-root xfs     20G  6.1G   14G  31% /
/dev/mapper/rhel-var  xfs     15G   15G   20K 100% /var
/dev/mapper/rhel-home xfs     10G  1.2G  8.8G  12% /home
/dev/sda1             xfs   1014M  987M   28M  98% /boot
tmpfs                 tmpfs  1.6G     0  1.6G   0% /run/user/0

/var is the problem, and /boot is close behind (usually too many old kernels). tmpfs lives in RAM. Ignore it for disk problems.

du --max-depth=1

24M     /var/spool
310M    /var/cache
1.1G    /var/lib
13G     /var/log
15G     /var

/var/log holds 13 of the 15 GB, so that's where to drill down next.

lsof +L1

COMMAND   PID  USER   FD   TYPE DEVICE    SIZE/OFF NLINK     NODE NAME
java     2314  app    12w   REG  253,2 9663676416     0  1048721 /var/log/app/app.log (deleted)

PID 2314 still has a 9 GB log file open for writing (12w = fd 12, write mode) that someone deleted with rm. NLINK 0 means no path points to it anymore. The space is only freed when that process closes fd 12 or exits.

df -i

Filesystem             Inodes  IUsed IFree IUse% Mounted on
/dev/mapper/rhel-var  7864320 7864320    0  100% /var

No inodes left: new files can't be created even though df -h may show free space.

Common problems

Log files have grown too large

Symptoms
/var/log or an application log directory is many GB, and one file keeps growing.
Possible causes
Debug logging left enabled, an error loop, a logrotate rule missing or never applied, or an application that writes its own logs outside logrotate's config.
Investigation
sudo du -sh /var/log/* 2>/dev/null | sort -h | tail
sudo tail -n 50 /var/log/app/app.log           # what is it logging?
sudo logrotate -d /etc/logrotate.conf 2>&1 | grep -A3 app   # would it rotate?
Resolution

Rotate the log if a rule exists. To empty an active log in place, truncate it. Do not rm it:

# Force rotation for one config (runs postrotate scripts, may restart/reload the service)
sudo logrotate -f /etc/logrotate.d/app

# Empty the file in place. The writing process keeps its descriptor and space is freed at once.
sudo truncate -s 0 /var/log/app/app.log
Warning

Truncating destroys the log contents. If the logs may be needed for an incident or audit, copy or compress them to another filesystem first. rm on a file that is still open frees no space and makes the problem harder to find (see the next section).

Verification
df -h /var shows the space returned, and the application keeps writing to the file.

Deleted files still using space

Symptoms
df reports 100%, but du totals far less. Someone recently ran rm on a large log.
Investigation
sudo lsof -nP +L1 | awk 'NR==1 || $7 > 100000000'    # open deleted files over ~100 MB
Resolution

The clean fix is to restart or reload the owning service so it reopens its log file:

sudo systemctl restart app.service

If a restart is not possible right now, you can truncate the deleted file through the process's descriptor:

# PID 2314, FD 12 from the lsof output above
sudo truncate -s 0 /proc/2314/fd/12
Warning

Double-check the PID and FD. Truncating the wrong descriptor (a database file, for example) corrupts data. Only use this on log files you are sure you can lose.

Inode exhaustion

Symptoms
No space left on device while df -h shows free space, and df -i shows 100%.
Possible causes
Session files, mail queue (/var/spool/postfix), cache directories, or a cron job that creates a small file on every run.
Investigation
sudo du --inodes -x --max-depth=1 /var 2>/dev/null | sort -n | tail
sudo du --inodes -x --max-depth=1 /var/lib/php 2>/dev/null | sort -n | tail
Resolution

Remove old files in the offending directory. Always print what would be deleted before deleting it:

sudo find /var/lib/php/sessions -xdev -type f -mtime +7 -print | head
sudo find /var/lib/php/sessions -xdev -type f -mtime +7 | wc -l
sudo find /var/lib/php/sessions -xdev -type f -mtime +7 -delete
Warning

Run find ... -delete only with the exact same path and filters you just previewed. -delete must come after the tests. Placed earlier, it deletes everything that find walks. Then fix whatever creates the files. XFS inode counts grow dynamically, but ext4's are fixed at mkfs time.

systemd journal using too much space

Investigation
journalctl --disk-usage
sudo du -sh /var/log/journal /run/log/journal 2>/dev/null

/var/log/journal exists when the journal is persistent. Otherwise it lives in /run (RAM) and is lost on reboot.

Resolution
sudo journalctl --vacuum-size=1G     # keep at most 1 GB of archived journals
sudo journalctl --vacuum-time=14d    # or: drop archived entries older than 14 days

Make the limit permanent in /etc/systemd/journald.conf, then restart journald:

[Journal]
SystemMaxUse=1G
SystemKeepFree=2G
sudo systemctl restart systemd-journald

Vacuuming only removes archived journal files, not the active one. Never delete files under /var/log/journal with rm.

Package cache and old kernels

Investigation
sudo du -sh /var/cache/dnf /var/cache/yum 2>/dev/null
rpm -q kernel
uname -r                                    # the running kernel
grep installonly_limit /etc/dnf/dnf.conf    # how many kernels dnf keeps (default 3)
Resolution
# Safe: cached metadata and packages are downloaded again when needed
sudo dnf clean all

# RHEL 8/9: remove old kernels, keeping the newest 2
sudo dnf remove --oldinstallonly --setopt installonly_limit=2 kernel
Warning

Check that dnf is not going to remove the running kernel (uname -r), and always keep at least one known-good fallback kernel. Never delete files in /boot by hand. The bootloader entries and initramfs files must stay consistent with installed packages.

Container storage (Podman / Docker)

Investigation
podman system df            # images, containers, volumes, and what is reclaimable
docker system df            # same, if Docker is used
sudo du -sh /var/lib/containers/storage /var/lib/docker 2>/dev/null
du -sh ~/.local/share/containers/storage        # rootless podman, per user
Resolution
podman image prune          # dangling (untagged) images only
podman container prune      # stopped containers
podman system prune         # both, plus unused networks and build cache
Warning

podman system prune -a (or docker system prune -a) removes every image not used by a running container, and --volumes also deletes unused volumes, which may hold data. Never delete directories under /var/lib/containers or /var/lib/docker directly. That corrupts the storage metadata. On Kubernetes/OpenShift nodes, let the kubelet's image garbage collection manage images instead of pruning by hand.

For Docker, cap container log growth in /etc/docker/daemon.json:

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

Files hidden under a mount point

Symptoms
/ is full, du -x / doesn't account for it, and lsof +L1 shows nothing.
Investigation

Bind-mount the root filesystem somewhere else to see what lies underneath the mount points:

sudo mkdir -p /mnt/rootfs
sudo mount --bind / /mnt/rootfs
sudo du -sh /mnt/rootfs/data /mnt/rootfs/var 2>/dev/null
sudo umount /mnt/rootfs
Resolution
Move the hidden files to where they belong (the real mounted filesystem), usually during a maintenance window with the application stopped.

The data is legitimate: extend the filesystem

Investigation
sudo vgs            # VFree: unallocated space in the volume group
sudo lvs
Resolution
# Grow the LV by 10 GB and resize the filesystem in the same step (-r)
sudo lvextend -r -L +10G /dev/rhel/var

XFS can grow online but can never be shrunk. Add only what you need, and take a snapshot or backup of critical systems first.

Troubleshooting tips

  • On a completely full /, even tab-completion or sort (which writes temp files) can fail. Free a few MB first, for example with dnf clean all or journalctl --vacuum-size.
  • Use ncdu -x / (from EPEL) for interactive browsing if it's available. It is read-only until you press d.
  • du on large trees or NFS can be slow. Scope it to the full filesystem with -x and drill down level by level.
  • Check /var/crash (kdump vmcores) and coredumpctl list. A single crash dump can be many GB.
  • On ext4, tune2fs -l /dev/mapper/... | grep -i 'reserved block' shows the root reserve, which explains why "Avail" is less than "Size − Used".

Best practices

  • Separate filesystems (or LVs) for /var, /var/log, /tmp and application data, so a runaway log can't fill /.
  • Every application log should have a logrotate rule, or log to journald with limits set.
  • Alert at 80–85% (and on inode usage), not at 100%.
  • Keep some free extents in the volume group for emergencies.
  • Truncate or rotate active logs. Never rm them.
  • Preview every find before adding -delete, and never run cleanup commands with unquoted globs or variables that might be empty (rm -rf "$DIR"/* with an empty $DIR expands to /*).

Summary

  1. df -hT and df -i: which filesystem, and is it blocks or inodes?
  2. du -xh --max-depth=1: drill down to the biggest directory.
  3. find -size / -mmin: large or fast-growing files.
  4. lsof +L1: if df and du disagree.
  5. Clean up with the owning tool (journalctl, dnf, podman, logrotate), truncate rather than delete active logs, then fix the cause or extend the volume.
