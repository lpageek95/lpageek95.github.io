Introduction

"It's DNS" is often true, but "DNS" covers several layers: the application's resolver library, /etc/hosts, a local caching stub, the configured recursive servers, and the authoritative servers for the zone. Most wasted time comes from testing the wrong layer, for example running dig (which bypasses the OS resolver) to debug an application that reads /etc/hosts.

When this is useful

  • An application reports Name or service not known, Temporary failure in name resolution or UnknownHostException.
  • A name resolves on one host but not another, or to different addresses.
  • A DNS change "isn't working yet".
  • Logins, SSH or Kerberos are slow (often reverse-lookup timeouts).
  • You're running or changing a BIND server.

Prerequisites

  • dig, host and nslookup come from bind-utils on RHEL (dnf install bind-utils).
  • resolvectl only applies when systemd-resolved is running. It is the default on Fedora and Ubuntu, but not on RHEL.
  • Examples use documentation names and addresses (example.com, 192.0.2.0/24, 10.0.0.0/8).

How resolution works on Linux

When a program calls getaddrinfo() (as curl, ssh, Java and Python do):

  1. /etc/nsswitch.conf decides the order of sources. The hosts: line is typically files dns myhostname.
  2. files means /etc/hosts. A match here wins, and DNS is never asked.
  3. dns means the glibc stub resolver, configured by /etc/resolv.conf. It sends the query to a nameserver, which is either a recursive server on the network or a local stub such as 127.0.0.53 (systemd-resolved).
  4. The recursive resolver answers from its cache or walks the hierarchy (root → .com → example.com's authoritative servers) and caches the result for the record's TTL.

/etc/resolv.conf

# Generated by NetworkManager
search corp.example.com example.com
nameserver 10.0.0.53
nameserver 10.0.1.53
options timeout:2 attempts:2
  • nameserver: up to 3 are used, tried in order. The second is only tried after the first times out, so a dead first server makes every lookup slow rather than failing.
  • search: suffixes appended to short names. getent hosts db01 tries db01.corp.example.com, then db01.example.com.
  • options ndots:n: names with fewer than n dots are tried with the search suffixes first (default 1). Kubernetes pods use ndots:5, which is why external lookups from pods can generate several NXDOMAIN queries first.
Who owns resolv.conf?

On RHEL, NetworkManager writes /etc/resolv.conf. Manual edits are overwritten on the next connection change. If it is a symlink to /run/systemd/resolve/stub-resolv.conf, systemd-resolved owns it. Check with ls -l /etc/resolv.conf before editing anything.

Troubleshooting workflow

1. Reproduce the failure the way the application sees it

getent hosts app.example.com     # uses nsswitch: /etc/hosts, then DNS, with search domains
getent ahosts app.example.com    # getaddrinfo(), shows every returned address (IPv4 and IPv6)

If getent works, name resolution on this host works, and the problem is elsewhere (application cache, proxy, firewall). If it fails, continue.

2. Check local overrides and resolver configuration

grep -v '^#' /etc/hosts
grep '^hosts:' /etc/nsswitch.conf
ls -l /etc/resolv.conf && cat /etc/resolv.conf
nmcli device show | grep -i dns          # what NetworkManager thinks the DNS servers are
resolvectl status                        # only if systemd-resolved is in use

Look for stale /etc/hosts entries, missing or wrong nameserver lines, and a wrong search list.

3. Query the configured server directly

dig app.example.com                      # uses the first nameserver in resolv.conf
dig @10.0.0.53 app.example.com A         # ask a specific server
dig @10.0.1.53 app.example.com A         # ...and the second one: do they agree?

dig talks DNS directly. It ignores /etc/hosts and nsswitch, and does not use the search list unless you add +search. Always query the fully qualified name.

4. Compare with an independent resolver and the authoritative servers

dig @8.8.8.8 example.com                 # public resolver (only if the host has outbound DNS)
dig example.com NS +short                # which servers are authoritative?
dig @ns1.example.com app.example.com +norecurse   # ask the authority directly, no cache involved
dig app.example.com +trace               # follow delegation from the root

If the authoritative server has the right answer but your recursive server doesn't, the issue is caching or forwarding on the recursive side. If the authoritative answer is wrong, the zone data is wrong.

5. Rule out the network path

dig @10.0.0.53 app.example.com +tcp      # does TCP/53 work where UDP/53 fails?
sudo tcpdump -ni any port 53             # are queries leaving and replies coming back?

DNS uses UDP/53 and falls back to TCP/53 for large responses (DNSSEC, many records). Firewalls that only allow UDP cause truncated or failed large answers.

6. Consider caches

Every layer may cache: the application (for example, the JVM), nscd/sssd, systemd-resolved, the recursive server, and even upstream forwarders. After a record change, old answers can persist for up to the old TTL. Failed lookups (NXDOMAIN) are cached too, for the SOA's negative TTL.

Commands and examples

dig example.com                 # default query: A record, full output
dig @8.8.8.8 example.com        # query a specific server
dig example.com A               # IPv4 address
dig example.com AAAA            # IPv6 address
dig example.com MX              # mail servers
dig example.com NS              # authoritative name servers
dig example.com SOA +short      # serial and timers
dig -x 192.0.2.10               # reverse (PTR) lookup
dig example.com +short          # answer only, handy in scripts
host app.example.com            # quick lookup (uses the search list)
nslookup app.example.com 10.0.0.53
resolvectl query app.example.com
ping -c1 app.example.com        # resolves via getaddrinfo, but ICMP may be blocked

Reading dig output

; <<>> DiG 9.16.23-RH <<>> app.example.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 40217
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;app.example.com.               IN      A

;; ANSWER SECTION:
app.example.com.        300     IN      CNAME   web01.example.com.
web01.example.com.      300     IN      A       192.0.2.10

;; Query time: 3 msec
;; SERVER: 10.0.0.53#53(10.0.0.53)
;; WHEN: Tue Sep 29 09:12:44 UTC 2026
;; MSG SIZE  rcvd: 82
  • status: the result code (see the table below). This is the first thing to read.
  • flags: qr is a response, rd means recursion desired, and ra means recursion available (the server is a recursive resolver). aa (authoritative answer) appears when you query the zone's own server.
  • ANSWER: app is a CNAME pointing to web01, which has the A record. The number (300) is the remaining TTL in seconds. From a cache, it counts down.
  • SERVER: which server answered. Confirm it's the one you meant to test.
  • Query time: 0–5 ms usually means a cached answer, and hundreds of ms means a full recursive lookup.
ResultMeaningUsual cause
NOERROR + answerSuccessCheck whether the address is the expected one
NOERROR, ANSWER: 0Name exists, but has no record of this type ("NODATA")For example, asking for AAAA when only A exists
NXDOMAINName does not existTypo, missing record, wrong zone, wrong search suffix, or a cached negative answer
SERVFAILThe server couldn't produce an answerDNSSEC validation failure, authoritative servers unreachable, broken delegation, zone failed to load

Common problems

dig works, the application doesn't

Symptoms
dig app.example.com returns the right address, but the application connects to the wrong host or fails to resolve.
Possible causes
A stale /etc/hosts entry, a different nsswitch order, a short name being expanded with the wrong search suffix, or the application's own DNS cache.
Investigation
getent ahosts app.example.com
grep -i app /etc/hosts
getent hosts app            # short name: which suffix wins?
Resolution
Remove the stale hosts entry, use fully qualified names in configuration, or restart the application to clear its cache (Java: check networkaddress.cache.ttl).

Every lookup is slow (seconds), but eventually works

Cause
The first nameserver in /etc/resolv.conf is unreachable, so every query waits for the timeout (5s by default) before trying the next one. Another cause is AAAA lookups timing out on a network without working IPv6 DNS.
Investigation
for ns in $(awk '/^nameserver/{print $2}' /etc/resolv.conf); do
  echo "== $ns"; dig @"$ns" example.com +short +time=2 +tries=1
done
Resolution (NetworkManager)
sudo nmcli connection modify eth0 ipv4.dns "10.0.0.53 10.0.1.53" ipv4.ignore-auto-dns yes
sudo nmcli connection up eth0

Bringing a connection up again over SSH can drop your session if the change is wrong. Have console access for remote hosts.

DNS change "not visible yet"

Investigation
dig @ns1.example.com app.example.com +norecurse   # authoritative: is the new value there?
dig @ns2.example.com app.example.com +norecurse   # all authoritative servers agree?
dig example.com SOA +short                        # serial number, then compare across servers
dig @10.0.0.53 app.example.com                    # recursive: TTL still counting down on the old answer?
Resolution
If the authoritative servers disagree, zone transfer or serial increment failed (see BIND checks). If only the recursive server is stale, wait out the TTL or flush it: 
sudo rndc flushname app.example.com     # BIND recursive server
sudo resolvectl flush-caches            # systemd-resolved on the client

Before a planned change, lower the record's TTL in advance (at least one old-TTL period before the change).

SERVFAIL for one domain

Investigation
dig broken.example.net                  # SERVFAIL
dig broken.example.net +cd              # +cd = checking disabled (skip DNSSEC validation)
dig broken.example.net +trace
Interpretation
If +cd returns an answer but a normal query returns SERVFAIL, DNSSEC validation is failing (expired signatures, broken DS record). That is the zone owner's problem to fix. Don't disable validation globally. If +trace stalls at one delegation, those authoritative servers are unreachable or misconfigured.

Slow SSH logins / missing reverse DNS

Investigation
dig -x 192.0.2.25 +short                 # PTR for the client's IP
dig $(dig -x 192.0.2.25 +short) +short   # forward-confirm: does the name map back to the IP?
Resolution
Add the correct PTR record in the reverse zone (for example 2.0.192.in-addr.arpa), or fix the reverse-zone server that is timing out. Kerberos, some mail servers and TLS setups depend on forward and reverse DNS matching.

BIND server checks

On a BIND (named) server on RHEL, check configuration and zone syntax before every reload:

sudo named-checkconf                         # syntax of /etc/named.conf
sudo named-checkconf -z                      # ...and load every zone it references
sudo named-checkzone example.com /var/named/example.com.zone
sudo named-checkzone 2.0.192.in-addr.arpa /var/named/192.0.2.rev
sudo rndc status
sudo journalctl -u named --since "30 min ago"
zone example.com/IN: loaded serial 2026092901
OK
sudo rndc reload example.com                 # reload one zone after editing it

Frequent BIND mistakes:

  • Serial not incremented. Secondaries never pick up the change. The YYYYMMDDnn format makes this easy to get right.
  • Missing trailing dot. web01.example.com without a dot inside the example.com zone becomes web01.example.com.example.com.
  • CNAME at the apex or next to other records at the same name.
  • ACLs: clients get REFUSED because allow-query or allow-recursion does not include their subnet.
  • SELinux / permissions: zone files copied in with the wrong context fail to load. ls -Z /var/named shows the context, and restorecon -Rv /var/named (which changes the system) restores the defaults.

Troubleshooting tips

  • Always test with the fully qualified name and a trailing dot (app.example.com.) to take search domains out of the picture.
  • Test each configured nameserver separately. Split-brain answers between two resolvers produce "intermittent" issues.
  • Record the SERVER line and TTL in tickets. They show which resolver and how stale the answer was.
  • In containers and pods, check the pod's own /etc/resolv.conf (kubectl exec <pod> -- cat /etc/resolv.conf). Cluster DNS (CoreDNS, which on OpenShift runs in the openshift-dns namespace) is a separate layer from the node's resolver.
  • ping failing doesn't mean DNS is failing. Check whether ping printed a resolved IP before timing out.

Best practices

  • Configure at least two resolvers, in different failure domains, and monitor both.
  • Manage client DNS through NetworkManager (or your config management), not by hand-editing /etc/resolv.conf.
  • Keep /etc/hosts minimal and documented. Hidden overrides are a classic cause of "works here, not there".
  • Use fully qualified names in application configs.
  • Lower TTLs before migrations, and restore them afterwards.
  • Run named-checkconf -z and named-checkzone in change procedures or CI before any reload.
  • Maintain PTR records for servers. Many tools and logs rely on them.

Summary

  1. getent ahosts: reproduce what the application sees.
  2. /etc/hosts, nsswitch.conf, resolv.conf: check the local configuration.
  3. dig @server name: test each configured resolver with the FQDN.
  4. dig +norecurse / +trace: compare with the authoritative source.
  5. Check the network (+tcp, tcpdump) and every cache layer.
  6. Read status first: NXDOMAIN, SERVFAIL, REFUSED and timeouts each point to a different layer.
