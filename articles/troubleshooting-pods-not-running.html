Troubleshooting Kubernetes / OpenShift Pods That Are Not Running

A repeatable workflow for finding out why a pod is stuck in Pending, ContainerCreating, Init, ImagePullBackOff, CrashLoopBackOff or Terminating, and what to do about each.

Introduction

The STATUS column of kubectl get pods is a summary, not a diagnosis. It tells you which stage of the pod lifecycle failed: scheduling, volume setup, image pull, init containers, the main container, or shutdown. Each stage leaves evidence in a different place. Knowing where to look for each one is most of the work.

All commands below use kubectl. On OpenShift, oc is a superset of kubectl: every kubectl get/describe/logs command works identically with oc. OpenShift-specific commands are called out where they add something.

When this is useful

  • A new deployment or rollout never becomes ready.
  • Pods restart repeatedly, or the restart counter keeps climbing.
  • Pods are stuck after a node failure, drain or cluster upgrade.
  • An application works in one namespace or cluster but not another.

Prerequisites

  • kubectl or oc logged in to the cluster.
  • At least view access to the namespace. Node-level checks (describe node, oc debug node/...) need cluster-level permissions.
  • Metrics (kubectl top) need metrics-server. OpenShift ships this through its monitoring stack.

How pod status works

A pod has a phase (Pending, Running, Succeeded, Failed, Unknown), and every container in it has a state (Waiting, Running, Terminated) with a reason. The STATUS column shows the most relevant of these, which is why you see values like CrashLoopBackOff that aren't phases at all.

STATUS shownLifecycle stageWhere the evidence is
Pending (no node assigned)SchedulingPod events (FailedScheduling), node capacity/taints
ContainerCreatingSandbox, network, volumesPod events (FailedMount, FailedCreatePodSandBox)
Init:0/2, Init:Error, Init:CrashLoopBackOffInit containersInit container logs
ErrImagePull, ImagePullBackOffImage pullPod events (Failed pulling image)
CreateContainerConfigErrorContainer configPod events: missing Secret/ConfigMap/key
CrashLoopBackOff, Error, OOMKilledMain container runtimeLogs (--previous), Last State, exit code
Running but 0/1 READYReadiness probePod events (Readiness probe failed)
TerminatingShutdown / deletionFinalizers, node status, grace period

Kubernetes retries failed image pulls and container starts with an exponential back-off (10s, 20s, 40s… capped at 5 minutes). ImagePullBackOff and CrashLoopBackOff just mean "failed, now waiting before the next retry". The real error happened on the previous attempt.

Troubleshooting workflow

Work top-down. Each step narrows the problem to one lifecycle stage.

1. Find the failing pods and their status

kubectl get pods -n my-app -o wide

# Everything not Running/Completed, across all namespaces
kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded

-o wide adds the NODE column. A pending pod with no node is a scheduling problem. A pod that has a node is past scheduling. If all failing pods are on the same node, suspect the node rather than the application.

2. Describe the pod and read the Events

kubectl describe pod web-7d9c6b8f5-x2kqp -n my-app

Scroll straight to Events: at the bottom, then check State, Last State, Reason and Exit Code for each container. In most cases the root cause is spelled out in one of these fields.

3. Check namespace events in time order

kubectl get events -n my-app --sort-by=.lastTimestamp

# Only events for one pod
kubectl get events -n my-app --field-selector involvedObject.name=web-7d9c6b8f5-x2kqp

Namespace events show related objects too: ReplicaSets that cannot create pods (quota, admission, SCC), PVCs that cannot bind, and so on. By default, events are kept for only about one hour.

4. Read the logs, including the previous container

kubectl logs web-7d9c6b8f5-x2kqp -n my-app

# Logs of the container instance that crashed (essential for CrashLoopBackOff)
kubectl logs web-7d9c6b8f5-x2kqp -n my-app --previous

# Multi-container pods: pick a container, or take all of them
kubectl logs web-7d9c6b8f5-x2kqp -n my-app -c app
kubectl logs web-7d9c6b8f5-x2kqp -n my-app --all-containers

Logs only exist once a container has started. For Pending, ContainerCreating and image-pull failures there are no logs. Use the events.

5. Check the node

kubectl get nodes
kubectl describe node worker02
kubectl top nodes            # OpenShift: oc adm top nodes

In describe node, check Conditions (MemoryPressure, DiskPressure, PIDPressure, Ready), Taints, and Allocated resources (requested CPU/memory versus allocatable).

6. Get inside if you need to

# OpenShift: start a copy of the pod with a shell, even if the original crashes on start
oc debug pod/web-7d9c6b8f5-x2kqp -n my-app

# OpenShift: shell on a node, then use the host's tools (crictl, journalctl)
oc debug node/worker02
chroot /host
crictl ps -a
journalctl -u kubelet --since "15 min ago"

# Kubernetes: attach an ephemeral debug container to a running pod
kubectl debug -it web-7d9c6b8f5-x2kqp -n my-app --image=busybox:1.36 --target=app

oc debug pod/... creates a new temporary pod with the same spec and /bin/sh as the command, so you can inspect the filesystem, environment and mounted volumes without the application crashing underneath you.

Reading the output

kubectl get pods

NAME                     READY   STATUS             RESTARTS        AGE   IP            NODE
web-7d9c6b8f5-x2kqp      0/1     CrashLoopBackOff   6 (2m11s ago)   9m    10.128.2.41   worker02
api-5f7b9c4d8-8kz2m      0/1     Pending            0               4m    <none>        <none>
worker-6c8d7f9b4-q7lwn   0/1     ImagePullBackOff   0               3m    10.131.0.17   worker01
db-0                     0/1     ContainerCreating  0               5m    <none>        worker03
  • web: started and crashed 6 times. Read logs --previous.
  • api: no IP, no node, so the scheduler could not place it. Read its events.
  • worker: scheduled, but the image cannot be pulled. Read its events.
  • db-0: scheduled to worker03 but stuck before start, usually a volume. Read its events.

kubectl describe pod (container section)

Containers:
  app:
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

Last State describes the previous instance, the one that died. Here the container exceeded its 256Mi memory limit and was killed by the kernel OOM killer. Common exit codes:

Exit codeMeaningTypical cause
0Process exited normallyThe command finished. Long-running containers must not exit (for example, a shell script that ends)
1Application errorBad config, failed DB connection, unhandled exception. Check the logs
126Command not executableMissing execute bit, or permission denied (arbitrary UID on OpenShift)
127Command not foundWrong command/args, or binary not in the image
137SIGKILL (128+9)OOMKilled, or killed after the grace period (for example, after a failed liveness probe)
139SIGSEGV (128+11)Segfault in the application or a native library
143SIGTERM (128+15)Normal shutdown request. Unexpected if it happens repeatedly

Events

LAST SEEN   TYPE      REASON             OBJECT                    MESSAGE
4m          Warning   FailedScheduling   pod/api-5f7b9c4d8-8kz2m   0/6 nodes are available: 3 Insufficient memory, 3 node(s) had untolerated taint {node-role.kubernetes.io/master: }. preemption: 0/6 nodes are available: 3 No preemption victims found for incoming pod, 3 Preemption is not helpful for scheduling.
3m          Warning   Failed             pod/worker-6c8d7f9b4-q7lwn  Failed to pull image "registry.example.com/team/worker:1.8": initializing source docker://registry.example.com/team/worker:1.8: reading manifest 1.8 in registry.example.com/team/worker: manifest unknown
5m          Warning   FailedMount        pod/db-0                  MountVolume.SetUp failed for volume "config" : configmap "db-config" not found

Event messages are the most useful single source. The exact wording depends on the Kubernetes version and container runtime (CRI-O on OpenShift, containerd elsewhere), but the key phrases (Insufficient memory, manifest unknown, not found) are stable enough to search for. The scheduling message is broken down in detail in Kubernetes Pod Scheduling.

Common problems by status

Pending

Symptoms
STATUS Pending, NODE <none>, a FailedScheduling event.
Possible causes
  • Resource shortage: Insufficient cpu / Insufficient memory. Scheduling uses requests, not actual usage. A node at 20% CPU can still be "full" if its requests are fully allocated.
  • Taints: had untolerated taint. The pod has no matching toleration.
  • Selectors/affinity: didn't match Pod's node affinity/selector. On OpenShift, a project-level node selector also applies.
  • Unbound PVC: pod has unbound immediate PersistentVolumeClaims.
  • Quota: the pod is never created at all. The ReplicaSet shows exceeded quota in its events.
Investigation
kubectl describe pod api-5f7b9c4d8-8kz2m -n my-app | sed -n '/Events:/,$p'
kubectl describe node worker01 | grep -A 8 'Allocated resources'
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
kubectl get pvc -n my-app
kubectl describe resourcequota -n my-app
Resolution
Lower over-sized requests, add capacity, add the right toleration/selector, or fix the StorageClass/PVC. Don't remove taints from nodes to "make it fit". They are usually there on purpose.
Verification
The pod gets a node assigned and moves to ContainerCreating and then Running.

ContainerCreating (stuck)

Symptoms
The pod has a node but stays in ContainerCreating for minutes.
Possible causes
  • Missing ConfigMap/Secret mounted as a volume: MountVolume.SetUp failed ... configmap "db-config" not found.
  • Storage attach/mount failure: FailedAttachVolume, or Multi-Attach error for volume ... Volume is already exclusively attached to one node. A ReadWriteOnce volume is still held by a pod on another node, often after a node failure.
  • Network (CNI) failure: FailedCreatePodSandBox. The node's SDN/OVN pod is unhealthy, or the node has run out of pod IPs.
Investigation
kubectl get events -n my-app --field-selector involvedObject.name=db-0
kubectl get configmap,secret -n my-app
kubectl describe pvc data-db-0 -n my-app
kubectl get volumeattachments | grep pvc-          # which node holds the volume
oc get pods -n openshift-ovn-kubernetes -o wide    # OpenShift (OVN-Kubernetes) network pods
Resolution
Create the missing object in the correct namespace (names are case-sensitive and namespaced). For Multi-Attach, make sure the old pod or node really is gone before the volume is released. Never force-detach a volume that may still be written to.

CreateContainerConfigError (missing Secret or ConfigMap key)

Symptoms
The status shows CreateContainerConfigError. The events say Error: secret "db-credentials" not found or couldn't find key DB_HOST in ConfigMap my-app/app-config.
Cause
An env/envFrom reference points to an object or key that doesn't exist. Volumes fail with FailedMount instead. Environment references fail here.
Resolution
Create the object or fix the key name. If the reference is truly optional, mark it optional: true. The kubelet retries automatically, so no restart is needed.

ErrImagePull / ImagePullBackOff

Symptoms
ErrImagePull on the first failure, then ImagePullBackOff while waiting to retry.
Possible causes (match the event message)
Message containsCause
manifest unknown / not foundWrong image name or tag, or the tag was deleted
unauthorized / authentication requiredMissing or wrong pull secret
x509: certificate signed by unknown authorityPrivate registry CA not trusted by the nodes
toomanyrequestsRegistry rate limit (common with Docker Hub)
i/o timeout / no such hostNode can't reach the registry: DNS, proxy, firewall
Investigation
kubectl get pod worker-6c8d7f9b4-q7lwn -n my-app -o jsonpath='{.spec.containers[*].image}{"\n"}'
kubectl get pod worker-6c8d7f9b4-q7lwn -n my-app -o jsonpath='{.spec.imagePullSecrets}{"\n"}'

# OpenShift: try the pull from the node itself
oc debug node/worker01
chroot /host
crictl pull registry.example.com/team/worker:1.8
Resolution (authentication)
kubectl create secret docker-registry regcred -n my-app \
  --docker-server=registry.example.com \
  --docker-username=robot-pull \
  --docker-password='<token>'

# Kubernetes: attach the secret to the service account the pod uses
kubectl patch serviceaccount default -n my-app \
  -p '{"imagePullSecrets":[{"name":"regcred"}]}'

# OpenShift equivalent
oc secrets link default regcred --for=pull -n my-app

The kubectl patch above replaces the whole imagePullSecrets list. If the service account already has pull secrets, add the new one to the list instead. Use a read-only robot/service account for pulls, never a personal login.

Init:0/N, Init:Error, Init:CrashLoopBackOff

Symptoms
The status shows Init:0/2 for a long time, or Init:CrashLoopBackOff. The main containers never start.
Cause
Init containers run one after another, and each must exit 0 before the next starts. Typical failures: a "wait for database" loop that never succeeds, a migration job that fails, or a permission error writing to a shared volume.
Investigation
# List init container names, then read the one that is failing
kubectl get pod web-7d9c6b8f5-x2kqp -n my-app -o jsonpath='{.spec.initContainers[*].name}{"\n"}'
kubectl logs web-7d9c6b8f5-x2kqp -n my-app -c wait-for-db
kubectl logs web-7d9c6b8f5-x2kqp -n my-app -c wait-for-db --previous
Resolution
Fix whatever the init container depends on (Service name, DNS, credentials, NetworkPolicy). For a wait loop, test the same check yourself from a debug pod in the same namespace.

CrashLoopBackOff

Symptoms
RESTARTS keeps increasing. The container runs for seconds or minutes, then dies.
Possible causes
  • Application crash: exit code 1 with a stack trace in logs --previous.
  • OOMKilled: exit code 137, Reason: OOMKilled. The memory limit is too low for the workload (JVMs are a classic example), or there is a real memory leak.
  • Liveness probe too aggressive: events show Liveness probe failed and Container app failed liveness probe, will be restarted. Often the app just starts slower than initialDelaySeconds allows. Use a startupProbe.
  • Container exits by design: exit code 0. The command runs once and ends, but the controller (a Deployment) expects it to keep running.
  • OpenShift security context: Permission denied on files or ports. With the restricted-v2 SCC, containers run as a random non-root UID and cannot bind ports below 1024. Build images that work with an arbitrary UID in the root group.
Investigation
kubectl logs web-7d9c6b8f5-x2kqp -n my-app --previous --tail=100
kubectl describe pod web-7d9c6b8f5-x2kqp -n my-app | grep -A 6 'Last State'

# OpenShift: which SCC admitted the pod
oc get pod web-7d9c6b8f5-x2kqp -n my-app -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
Resolution
Fix the application or its config, size memory limits based on observed usage, and relax probe timings. Don't grant anyuid or privileged SCCs just to get past a permission error. Fix the image instead.

Running but not Ready

Symptoms
STATUS Running, READY 0/1, and no restarts. The Service returns 503 or times out.
Cause
The readiness probe fails. The container is not restarted, but it is removed from Service endpoints.
Investigation
kubectl describe pod web-7d9c6b8f5-x2kqp -n my-app | grep -iE 'readiness|probe'
kubectl get endpointslices -n my-app -l kubernetes.io/service-name=web
Resolution
Check that the probe path/port matches what the app actually serves, and that its dependencies are up. A readiness probe that checks downstream services can take every replica out of rotation at once. Keep it focused on the pod itself.

Terminating (stuck)

Symptoms
The pod has shown Terminating for much longer than its terminationGracePeriodSeconds.
Possible causes
  • Node is NotReady/unreachable: the kubelet can't confirm the containers stopped, so the API object stays.
  • Finalizers: a controller must clean something up first, and that controller is broken or gone.
  • Long preStop hook or grace period.
Investigation
kubectl get pod db-0 -n my-app -o jsonpath='{.metadata.deletionTimestamp}{"  "}{.metadata.finalizers}{"\n"}'
kubectl get node worker03
Resolution

Fix the node or the controller that owns the finalizer first. Force deletion is a last resort:

kubectl delete pod db-0 -n my-app --grace-period=0 --force
Warning: force delete

This only removes the API object. The container may still be running on an unreachable node. For StatefulSets this can result in two pods with the same identity writing to the same volume. Confirm the node is really down (or powered off) first. Removing finalizers by hand (kubectl patch ... finalizers:null) skips cleanup and can leave orphaned resources behind.

Troubleshooting tips

  • Events expire. Capture them early (kubectl get events -n ns > events.txt) when handing an issue over.
  • Compare with a working pod. kubectl get pod good -o yaml versus the broken one often shows the difference immediately (image tag, env var, node).
  • Look at the controller too. If no pod exists at all, kubectl describe deploy/web and describe rs will show quota or admission errors.
  • One node, many failures? Cordon it (kubectl cordon worker02, which changes the system) to stop new pods landing there while you investigate.
  • Deleting a pod is not a fix. The controller recreates it with the same spec. It helps only for transient node or volume problems.
  • OpenShift: oc status --suggest gives a quick overview of a project, and oc adm must-gather collects diagnostic data for support cases.

Best practices

  • Set realistic requests and limits based on measured usage. Requests drive scheduling, and limits drive OOM kills and CPU throttling.
  • Use a startupProbe for slow-starting apps, and keep liveness probes simple (the process is alive) and readiness probes pod-local.
  • Pin images by tag or digest, never :latest in production.
  • Build images that run as an arbitrary non-root UID. They work on OpenShift's default SCC and are safer everywhere.
  • Log to stdout/stderr so kubectl logs works, and ship logs to central storage so they survive pod deletion.
  • Use PodDisruptionBudgets and multiple replicas so that one failing pod doesn't cause an outage.

Summary

  1. get pods -o wide: which stage failed, and on which node?
  2. describe pod: read Events, Last State and the exit code.
  3. get events --sort-by=.lastTimestamp: see the timeline and related objects.
  4. logs --previous: why did the container die?
  5. describe node: capacity, taints and conditions.
  6. Fix the cause in the manifest or environment. Deleting or restarting pods rarely fixes anything by itself.
