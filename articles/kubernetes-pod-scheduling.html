Introduction

Placement rules come in two directions. Selectors and affinity are set on the pod and say "run me on nodes like this". Taints are set on the node and say "keep pods off me unless they explicitly tolerate this". Most scheduling surprises come from mixing the two up, especially from expecting a toleration to attract a pod to a node. It doesn't.

When this is useful

  • Pods are stuck in Pending with a FailedScheduling event.
  • Dedicating nodes to a workload class: infra, GPU, databases, a specific team.
  • Spreading replicas across nodes or zones for availability.
  • Moving OpenShift router, registry or monitoring components to infra nodes.

Prerequisites

  • kubectl or oc access. Labelling and tainting nodes requires cluster-admin-level permissions.
  • A basic understanding of Deployments, labels and pod status.

How the scheduler works

The scheduler (kube-scheduler, which on OpenShift runs in openshift-kube-scheduler) watches for pods with no spec.nodeName. For each one:

  1. Filter: discard nodes that can't run the pod: not enough allocatable CPU/memory for the pod's requests, untolerated taints, non-matching selectors or required affinity, volume topology conflicts, host port conflicts, unschedulable (cordoned) nodes.
  2. Score: rank the remaining nodes (preferred affinity, spreading, resource balance, image locality).
  3. Bind: write the chosen node into spec.nodeName. The kubelet on that node starts the pod.

If filtering leaves zero nodes, the pod stays Pending, and the scheduler records why each node was rejected in a FailedScheduling event. It then tries preemption: evicting lower-priority pods to make room, if the pod has a higher PriorityClass.

Scheduling uses requests, not usage

A node at 15% actual CPU can reject a pod with Insufficient cpu if the sum of requests on it is close to allocatable. Check kubectl describe node → Allocated resources.

Attracting pods: nodeSelector and node affinity

Labels

kubectl get nodes --show-labels
kubectl get nodes -L disktype,topology.kubernetes.io/zone    # show chosen labels as columns
kubectl label node worker03 disktype=ssd
kubectl label node worker03 disktype-           # remove the label

nodeSelector

The simplest rule: the node must have all of these labels, with these exact values.

apiVersion: v1
kind: Pod
metadata:
  name: pg-bench
spec:
  nodeSelector:
    disktype: ssd
  containers:
  - name: bench
    image: registry.example.com/tools/pgbench:16

Node affinity

Node affinity adds operators (In, NotIn, Exists, DoesNotExist, Gt, Lt) and soft preferences:

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:                    # expressions in one term are ANDed
          - key: topology.kubernetes.io/zone
            operator: In
            values: ["eu-west-1a", "eu-west-1b"]
          - key: node-role.kubernetes.io/infra
            operator: DoesNotExist
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80                             # 1-100, added to the node's score
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values: ["ssd"]
  • required... is a hard filter. Multiple nodeSelectorTerms are ORed.
  • preferred... only influences scoring. The pod still runs elsewhere if no node matches.
  • IgnoredDuringExecution: changing node labels later does not evict running pods.

Pod affinity and anti-affinity

These rules place pods relative to other pods, within a topology domain defined by a node label (kubernetes.io/hostname = per node, topology.kubernetes.io/zone = per zone). A common use is keeping replicas of the same app on different nodes: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              topologyKey: kubernetes.io/hostname
              labelSelector:
                matchLabels: { app: web }
      containers:
      - name: web
        image: registry.example.com/team/web:2.3

Use preferred unless you truly need a hard guarantee. With required anti-affinity and replicas greater than the number of eligible nodes, the extra replicas stay Pending forever. For even spreading, topologySpreadConstraints is usually a better tool than anti-affinity.

Repelling pods: taints and tolerations

A taint has the form key=value:effect:

kubectl taint nodes worker01 dedicated=infra:NoSchedule

# Remove it again (note the trailing dash)
kubectl taint nodes worker01 dedicated=infra:NoSchedule-
kubectl describe node worker01 | grep -A3 Taints
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
EffectNew pods without a tolerationRunning pods without a toleration
NoScheduleNot scheduledKeep running
PreferNoScheduleAvoided if possible (soft)Keep running
NoExecuteNot scheduledEvicted (after tolerationSeconds, if set)

Tolerating the taint

spec:
  tolerations:
  - key: dedicated
    operator: Equal        # key, value and effect must match the taint
    value: infra
    effect: NoSchedule
  # operator: Exists matches any value for the key:
  # - key: dedicated
  #   operator: Exists
  #   effect: NoSchedule
A toleration only permits, it doesn't attract

The pod above may run on worker01, but the scheduler is just as happy to put it on any untainted node. To dedicate nodes, combine a taint (keep others off) with a label and a nodeSelector/affinity (pull these pods on). Also avoid a bare operator: Exists with no key. That tolerates every taint, including control-plane and NoExecute node-problem taints.

Taints Kubernetes adds by itself

TaintAdded when
node.kubernetes.io/not-ready:NoExecuteNode Ready condition is False
node.kubernetes.io/unreachable:NoExecuteNode controller lost contact with the node
node.kubernetes.io/unschedulable:NoScheduleNode was cordoned (kubectl cordon / drain)
node.kubernetes.io/memory-pressure, disk-pressure, pid-pressureKubelet reports resource pressure
node-role.kubernetes.io/master:NoSchedule / control-plane:NoScheduleControl plane nodes (OpenShift and kubeadm clusters)

Pods get default tolerations for not-ready and unreachable with tolerationSeconds: 300. That's why pods on a failed node are only evicted after about 5 minutes.

Example: dedicated OpenShift infra nodes

On OpenShift, cluster components such as the ingress router, the internal image registry and the monitoring stack can be moved to infra nodes. This keeps them away from application workloads (and, per Red Hat's subscription terms, infra nodes that only run these components don't need OpenShift subscriptions). The pattern is label + taint on the node, nodeSelector + toleration on the workload.

In production, set these in the infra MachineSet template (spec.template.spec.metadata.labels and spec.template.spec.taints) so new nodes get them automatically. The manual equivalent is:

oc label node infra01 node-role.kubernetes.io/infra=""
oc adm taint nodes infra01 node-role.kubernetes.io/infra=reserved:NoSchedule

Move the default ingress controller (router pods) onto them:

oc patch ingresscontroller/default -n openshift-ingress-operator --type=merge -p '
{"spec":{"nodePlacement":{
  "nodeSelector":{"matchLabels":{"node-role.kubernetes.io/infra":""}},
  "tolerations":[{"key":"node-role.kubernetes.io/infra","value":"reserved","effect":"NoSchedule"}]
}}}'

The image registry operator uses spec.nodeSelector and spec.tolerations in the same way:

oc patch configs.imageregistry.operator.openshift.io/cluster --type=merge -p '
{"spec":{
  "nodeSelector":{"node-role.kubernetes.io/infra":""},
  "tolerations":[{"key":"node-role.kubernetes.io/infra","value":"reserved","effect":"NoSchedule"}]
}}'

Operators installed through OLM accept placement in their Subscription:

apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator
  namespace: openshift-operators
spec:
  channel: stable
  name: my-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  config:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
oc get nodes -l node-role.kubernetes.io/infra
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-image-registry -o wide
OpenShift project node selectors

OpenShift can apply a node selector to every pod in a project, through the openshift.io/node-selector namespace annotation or the cluster-wide defaultNodeSelector in schedulers.config.openshift.io/cluster. It is merged with the pod's own selector. If the two conflict, the pod can never be scheduled. Check with oc get namespace my-app -o yaml | grep node-selector.

Troubleshooting workflow

1. Confirm it is a scheduling problem

kubectl get pods -n my-app -o wide              # Pending + NODE <none>
kubectl get events -A --field-selector reason=FailedScheduling

2. Read the pod's scheduling constraints

kubectl describe pod api-5f7b9c4d8-8kz2m -n my-app     # Node-Selectors, Tolerations, Events
kubectl get pod api-5f7b9c4d8-8kz2m -n my-app \
  -o jsonpath='{.spec.nodeSelector}{"\n"}{.spec.affinity}{"\n"}{.spec.tolerations}{"\n"}'
kubectl get pod api-5f7b9c4d8-8kz2m -n my-app \
  -o jsonpath='{range .spec.containers[*]}{.name}{" "}{.resources.requests}{"\n"}{end}'

3. Compare with what the nodes offer

kubectl get nodes -L node-role.kubernetes.io/infra,topology.kubernetes.io/zone
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
kubectl describe node worker01 | grep -A 10 'Allocated resources'

4. Fix the side that is wrong

Either the pod's rules are wrong (fix the manifest), or the nodes are missing a label/capacity (fix the nodes). Change one thing at a time and watch the pod's events for the new message.

With oc, every command above works as-is: replace kubectl with oc, and use oc adm taint / oc adm top nodes for the admin variants.

Reading FailedScheduling messages

Warning  FailedScheduling  2m  default-scheduler  0/6 nodes are available:
  3 node(s) had untolerated taint {node-role.kubernetes.io/master: },
  2 Insufficient memory,
  1 node(s) didn't match Pod's node affinity/selector.
  preemption: 0/6 nodes are available: 2 No preemption victims found for incoming pod,
  4 Preemption is not helpful for scheduling.

(Wrapped for readability. The real message is a single line.) Read it as: "of 6 nodes, none passed filtering":

  • 3 had an untolerated taint: the 3 control plane nodes. Expected, ignore them.
  • 2 Insufficient memory: 2 workers passed every other filter but don't have enough unrequested memory. This is the actionable part.
  • 1 didn't match the node selector/affinity: the pod's rules exclude that node, for example an infra node.
  • preemption: evicting lower-priority pods wouldn't help (or no lower-priority pods exist).

Counts usually add up to the node total, but a single node can appear under more than one reason (for example, both Insufficient cpu and Insufficient memory). Common reasons:

Common problems

Pod tolerates the infra taint but still lands on worker nodes

Cause
A toleration only permits placement. There is no nodeSelector or affinity pulling the pod to infra nodes.
Resolution
Add nodeSelector: {node-role.kubernetes.io/infra: ""} alongside the toleration.
Verification
kubectl get pods -o wide shows only infra nodes in the NODE column.

Pods evicted right after tainting a node

Cause
The taint used NoExecute, which evicts running pods that don't tolerate it. NoSchedule would only have affected new pods.
Resolution
Use NoSchedule first, move workloads deliberately (drain or roll out), and only then add NoExecute if you need it.

Some replicas are Pending after scaling up

Symptoms
didn't match pod anti-affinity rules for the extra replicas.
Cause
Required anti-affinity on kubernetes.io/hostname with more replicas than eligible nodes.
Resolution
Switch to preferred anti-affinity or topologySpreadConstraints with whenUnsatisfiable: ScheduleAnyway, or add nodes.

StatefulSet pod Pending after a node was replaced

Symptoms
had volume node affinity conflict.
Cause
The pod's PV is zonal (cloud block storage) or local, and no schedulable node exists in that zone or on that host.
Resolution
Bring a node back in that zone, or restore the data to a new volume. Use volumeBindingMode: WaitForFirstConsumer on StorageClasses so new volumes are created where the pod can actually run.

Troubleshooting tips

  • Ignore the reasons you expect (control plane taints) and focus on the nodes that should have fit.
  • Taint keys, values and effects must match exactly. dedicated=infra:NoSchedule is not tolerated by a toleration for dedicated=Infra.
  • Setting spec.nodeName by hand bypasses the scheduler entirely (no filtering, no events). Avoid it except for debugging.
  • DaemonSets tolerate some taints automatically (such as unschedulable and the node-pressure taints), but not custom ones like dedicated=infra. Add those tolerations explicitly if the DaemonSet must run on tainted nodes.
  • After fixing a node label or taint, the scheduler retries pending pods automatically. There's no need to delete them.

Best practices

  • Use taint + label + selector/toleration together for dedicated nodes, never a taint alone.
  • Manage node labels and taints through MachineSets / cloud node pools or config management, so replacement nodes get them too.
  • Prefer soft rules (preferred, PreferNoSchedule, ScheduleAnyway) unless a hard rule is a real requirement.
  • Set accurate resource requests. They are the most common reason pods don't fit.
  • Use well-known label keys (topology.kubernetes.io/zone, node-role.kubernetes.io/<role>) and document custom ones.
  • Keep headroom: leave enough spare capacity to reschedule the pods of your largest node.

Summary

  • nodeSelector / node affinity (on the pod) pull pods to nodes. Taints (on the node) push pods away unless they have a toleration.
  • NoSchedule blocks new pods, PreferNoSchedule is a soft version, and NoExecute also evicts running pods.
  • Dedicated nodes (for example OpenShift infra) need a label and a taint on the node, plus a selector and a toleration on the workload.
  • 0/N nodes are available lists why each node was rejected. Find the reason for the nodes that should have fit, and fix that.
